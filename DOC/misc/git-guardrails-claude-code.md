# git-guardrails-claude-code — защита от опасных git-команд

## Что делает

Ставит барьер перед разрушительными операциями git: копирует скрипт-обёртку `block-dangerous-git.sh`, который читает JSON с командой и решает, опасна ли она, и дописывает в `AGENTS.md` правило, обязывающее агента сверяться с этим скриптом перед любой командой `git`. Блокировка происходит до выполнения, а не после: команда не доходит до git.

Блокируются `git push` (все варианты, включая `--force`), `git reset --hard`, `git clean -f` / `git clean -fd`, `git branch -D`, `git checkout .` / `git restore .`. При блокировке агент видит сообщение о том, что у него нет полномочий использовать эти команды.

Скилл ничего не перехватывает сам — он собирает связку «скрипт плюс правило в `AGENTS.md`», которая и работает.

## Когда вызывать

- Пользователь хочет предотвратить разрушительные git-операции.
- Нужно добавить защитные ограничения для git.
- Нужно запретить агенту `git push` и/или `git reset`.

## Как работает

Пять шагов по порядку:

1. **Спрашивает область действия.** Установить только для этого проекта или для всех проектов — от ответа зависят оба пути:

   | Область | Скрипт | Правило |
   | --- | --- | --- |
   | Только проект | `.dsh/hooks/block-dangerous-git.sh` | `AGENTS.md` в корне репозитория |
   | Все проекты | `~/.dsh/hooks/block-dangerous-git.sh` | `~/.dsh/AGENTS.md` |

2. **Копирует скрипт.** Берёт встроенный `scripts/block-dangerous-git.sh` и копирует в целевое место по области действия, затем делает его исполняемым через `chmod +x`.

3. **Добавляет правило в `AGENTS.md`.** Для проекта:

   ```markdown
   ## Опасные git-команды

   Никогда не выполняй git-команды, которые блокирует `.dsh/hooks/block-dangerous-git.sh`. Перед любой командой `git` сверься со скриптом: `echo '{"tool_input":{"command":"<команда>"}}' | .dsh/hooks/block-dangerous-git.sh`. Код выхода 2 означает запрет: сообщи пользователю, что у тебя нет полномочий на эту команду, и не выполняй её.
   ```

   Глобально — тот же текст с `~/.dsh/hooks/block-dangerous-git.sh`. Если `AGENTS.md` уже существует, раздел добавляется к его содержимому; остальное не перезаписывается.

4. **Спрашивает про кастомизацию.** Пользователь может добавить или убрать паттерны из списка блокируемых — скопированный скрипт правится соответственно.

5. **Проверяет.** Запускает быстрый тест:

   ```bash
   echo '{"tool_input":{"command":"git push origin main"}}' | <path-to-script>
   ```

   Ожидание: код выхода 2 и сообщение о блокировке в stderr.

Что читает скрипт: JSON со stdin, команду достаёт через `jq -r '.tool_input.command'`. Дальше сверяет её по очереди с шаблонами из массива `DANGEROUS_PATTERNS` (`git push`, `git reset --hard`, `git clean -fd`, `git clean -f`, `git branch -D`, `git checkout \.`, `git restore \.`, `push --force`, `reset --hard`) через `grep -qE`. При первом совпадении печатает в stderr `ЗАБЛОКИРОВАНО: '<команда>' совпадает с опасным шаблоном '<шаблон>'. Пользователь запретил тебе это делать.` и завершается с кодом 2. Если ни один шаблон не совпал — код 0.

Чем заканчивается: скрипт лежит по выбранному пути и исполняем, в `AGENTS.md` появился раздел «Опасные git-команды», проверочный запуск вернул 2.

## Пример

Человек: «Запрети агенту делать `git push` и `git reset --hard` в этом репозитории».

1. Скилл спрашивает область действия. Ответ — только этот проект.
2. Копирует `scripts/block-dangerous-git.sh` из скилла в `.dsh/hooks/block-dangerous-git.sh` и делает исполняемым: `chmod +x .dsh/hooks/block-dangerous-git.sh`.
3. Дописывает в корневой `AGENTS.md` раздел «Опасные git-команды» с правилом для проекта, не трогая остальные разделы.
4. Спрашивает про кастомизацию. Человек оставляет список шаблонов по умолчанию.
5. Проверка проходит как ожидается:

   ```bash
   echo '{"tool_input":{"command":"git push origin main"}}' | .dsh/hooks/block-dangerous-git.sh
   ```

   Код выхода 2, в stderr: `ЗАБЛОКИРОВАНО: 'git push origin main' совпадает с опасным шаблоном 'git push'. Пользователь запретил тебе это делать.`

Дальше, когда агент захочет отправить ветку, правило из `AGENTS.md` велит ему сначала прогнать команду через `echo '{"tool_input":{"command":"git push origin main"}}' | .dsh/hooks/block-dangerous-git.sh`, получить код 2 и сообщить человеку, что полномочий на эту команду нет, — вместо того чтобы выполнить push. Отправку делает человек.

Результат: в репозитории появились `.dsh/hooks/block-dangerous-git.sh` и раздел в `AGENTS.md`, опасные команды не доходят до git.

## Грабли

- **Скрипт сам по себе ничего не перехватывает.** В DSH хуков Claude Code нет: файл в `.dsh/hooks/` не вызывается автоматически. Барьер держится на том, что агент прочитал правило в `AGENTS.md` и дисциплинированно сверяется через `echo … | <script>`; если правило не попало в контекст, команда пройдёт. Проверяйте, что `AGENTS.md` действительно загружается.
- **Нужен `jq`.** Скрипт разбирает stdin через `jq -r '.tool_input.command'`; без `jq` проверять команду нечем. Убедитесь, что он установлен, прежде чем считать защиту работающей.
- **Шаблоны — это регулярные подстроки.** Список короткий и совпадает по вхождению, поэтому блокируется любая команда, содержащая шаблон, а формы, которых в списке нет (в частности, иные варианты флагов), проходят мимо. Свои варианты добавляйте или убирайте на шаге кастомизации.
- **Пара «скрипт — правило» должна сходиться.** Правило в проектном `AGENTS.md` ссылается на `.dsh/hooks/…`, глобальное — на `~/.dsh/hooks/…`. Если правило и скрипт оказались в разных областях, `echo … |` укажет на несуществующий путь и проверка ничего не проверит. И не путайте `~/.dsh/hooks` с каталогом скиллов `~/.dsh/skills`.
- **Скилл в статусе in-progress и может меняться.** Состав шаблонов и текст скрипта способны поменяться — копируйте `scripts/block-dangerous-git.sh` из актуального источника скилла, а не по памяти, и после обновления скилла перепроверяйте уже установленную копию.
