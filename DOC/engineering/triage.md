# triage — входящие issue: категория, состояние, бриф

## Что делает

`triage` проходит по issue в трекере задач вашего проекта. Он проводит каждую через небольшую машину состояний из **ролей триажа** (роль категории и роль состояния). Каждая issue заканчивается брифом, готовым для агента, конкретным вопросом репортёру или закрытой issue с записанной причиной.

Он только для issue, **которые создали не вы**. То есть сырые баг-репорты, входящие запросы фич или внешний pull request, пришедший без предупреждения: работа, которая попала в трекер снаружи, в каком бы виде её ни оставил репортёр. [Тикеты](https://www.aihero.dev/ai-coding-dictionary/ticket) из [to-tickets](https://aihero.dev/skills-to-tickets) уже готовы к агенту, поэтому прогон `triage` по ним сжигает работу впустую. Правило простое: скилл `triage` — только для входящих issue, не для тех, что вы создали сами.

Ещё он отличается от ручной развески меток тем, что сначала рекомендует и ждёт. Он выдаёт своё решение по категории и состоянию с обоснованием — плюс то, что нашёл в кодовой базе, — и ничего не применяет, пока вы не скажете.

## Когда вызывать

Вы вызываете его, упомянув скилл `triage` и описав обычным языком, чего хотите. [Агент](https://www.aihero.dev/ai-coding-dictionary/agent) сам к нему не потянется. Примеры: «покажи, что требует моего внимания», «давай посмотрим #42», «переведи #42 в ready-for-agent».

| Что у вас | Куда идти |
| --- | --- |
| Трекер, забитый сырыми репортами других людей | скилл `triage` |
| Своя примерная идея, ничего не записано | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| Устоявшийся разговор, который пора превратить в [спеку](https://www.aihero.dev/ai-coding-dictionary/spec) | [to-spec](https://aihero.dev/skills-to-spec) |
| Спека, которую надо разбить на тикеты для агента | [to-tickets](https://aihero.dev/skills-to-tickets) |
| Подтверждённый баг, которому нужна первопричина, а не метка | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

## Требования

`triage` читает и пишет ваш трекер issue, поэтому [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) должен сначала настроить этот трекер и словарь его меток. Имена ролей ниже — **канонические**. Строки меток в вашем трекере могут отличаться, и setup даёт соответствие. Если трекер уже использует канонические имена точно, сопоставлять и настраивать нечего.

Конфиг трекера решает и другое: считаются ли внешние pull request'ы поверхностью запросов и кто считается внешним. Этот флаг по умолчанию выключен, и setup про него больше не спрашивает. Чтобы ввести PR в область действия, включите его в `docs/agents/issue-tracker.md`.

## Машина состояний

Каждый разобранный элемент заканчивается ровно одной ролью категории и ровно одной ролью состояния. Категорий две: `bug` (что-то сломано) и `enhancement` (новая фича или улучшение). Состояний пять:

| Состояние | Что означает |
| --- | --- |
| `needs-triage` | Вам нужно его оценить. Issue без меток обычно попадает сюда первой. |
| `needs-info` | Ждём репортёра. Возвращается в `needs-triage`, когда он ответит. |
| `ready-for-agent` | Полностью описано, бриф для агента приложен. [AFK](https://www.aihero.dev/ai-coding-dictionary/afk)-агент может взять это в работу. |
| `ready-for-human` | Тот же бриф плюс причина, почему агент не справится: суждение, внешний доступ, ручное тестирование. |
| `wontfix` | Закрыто, причина записана. |

Это весь словарь. Правило «ровно одно состояние на элемент» держит запросы простыми. Состояния — ещё и самая запрашиваемая область [скилла](https://www.aihero.dev/ai-coding-dictionary/skill). Люди просили состояние для работы, которая специфицирована, но заблокирована другой issue, состояние `deferred` для работы, ждущей будущего триггера, и терминальное состояние `implemented`. Ничего из этого не вышло. См. вопросы ниже.

У `wontfix` три случая. Разница важна, потому что только один из них пишет в базу знаний:

| Почему закрываете | Что происходит |
| --- | --- |
| Уже реализовано | Комментарий со ссылкой на то, где эта возможность уже живёт. В `.out-of-scope/` ничего не пишется: это построенная фича, а не отвергнутая, и файл там сломал бы проверки на дубликаты. |
| Отвергнутый баг | Вежливое объяснение, затем закрытие. |
| Отвергнутое улучшение | Файл в `.out-of-scope/`, ссылка на него из закрывающего комментария, затем закрытие. |

`.out-of-scope/` хранит по одному markdown-файлу на отвергнутый **концепт**, а не на issue. Каждый файл — короткий дизайн-документ, а не строка в базе данных. В нём сказано, что отвергли и почему, и перечислены все issue, которые этого просили. `triage` читает весь каталог, прежде чем что-то оценивать. Сопоставляет он по концепту, а не по ключевым словам, поэтому «ночная тема» совпадает с `dark-mode.md`. Найдя совпадение, он показывает вам старое решение и спрашивает, согласны ли вы с ним до сих пор, вместо того чтобы заново спорить о запросе с нуля.

## Проверка до брифа

Перед любым [гриллингом](https://www.aihero.dev/ai-coding-dictionary/grilling) `triage` проверяет, что утверждение верно. Для бага он воспроизводит его по шагам репортёра. Для PR он выкачивает ветку и прогоняет релевантные тесты. Затем сообщает один из трёх результатов:

- Подтверждено, с путём в коде.
- Не воспроизвелось.
- Деталей недостаточно, чтобы попробовать. Это самый сильный сигнал к `needs-info`, какой бывает.

В том же проходе он делает ещё две проверки по кодовой базе. Проверка **избыточности** спрашивает, не реализована ли фича уже, и ищет по доменному концепту, а не по формулировке репортёра. Проверка **прежнего отказа** спрашивает, не сказано ли уже «нет» в `.out-of-scope/`. Обе дешёвые, и попадание в любую даёт `wontfix`.

Вся эта работа делает хорошим один артефакт: **бриф для агента**. Это структурированный комментарий, который `triage` публикует, когда issue переходит в `ready-for-agent`. После публикации бриф становится контрактом, а исходный репорт — только контекстом. Брифы **долговечны**, а не точны, потому что issue может неделями висеть в `ready-for-agent`, пока код меняется. Поэтому бриф называет типы, сигнатуры и контракты поведения и никогда — пути к файлам и номера строк. Подтверждённое воспроизведение даёт гораздо более сильный бриф, чем догадка.

## PR — это issue с приложенным кодом

Если трекер считает внешние pull request'ы поверхностью запросов, они проходят ту же машину, с теми же категориями, состояниями и переходами. Состояния относятся к дифу. `ready-for-agent` означает, что бриф приложен и агенту пора делать следующий шаг по коду. `ready-for-human` означает, что человек может слить. Бриф на PR описывает, что осталось сделать с уже существующим дифом, а не как построить вещь с нуля.

Обнаружение показывает только *внешние* PR: незавершённая ветка коллеги — не работа для триажа. Этот фильтр действует только на обнаружение. Если вы назвали PR явно, `triage` его разберёт, кто бы его ни написал.

## Частые вопросы

**Я прогнал `to-spec` и `to-tickets`, и теперь эти тикеты висят неразобранными. Гонять по ним `triage`?**
Нет. Они уже готовы к агенту. `to-tickets` ставит метку `ready-for-agent`, когда публикует их, поэтому AFK-раннер подхватит их без ещё одного прохода. Пользователь, который на это наткнулся, прогнал поток спеки, увидел `needs-triage` на выходе — и его AFK-раннер проигнорировал всё. `triage` — это въездная полоса для работы, приходящей снаружи. Поток спеки — полоса для работы, которую вы начинаете сами. Сходятся они на `ready-for-agent`, но не раньше.

**`triage` ещё актуален, когда есть поток `to-spec` → `to-tickets` → `implement`?**
Только если у вас есть входящая работа. `triage` старше этого потока и делает другое: разбирает репорты, которые завели другие люди. Если всё в вашем трекере пришло из вашего же планирования, он вам понадобится редко. Если вы поддерживаете что-то публичное или команда заводит баги на вас, работа начинается именно здесь. Основное применение — open-source репозитории, принимающие issue от внешних контрибьюторов.

**Агент попробовал поставить `ready-for-agent`, и `gh` сказал, что такой метки нет.**
Это известный открытый баг ([#616](https://github.com/mattpocock/skills/issues/616)). `setup-matt-pocock-skills` записывает словарь меток в `docs/agents/triage-labels.md`, но сами метки в трекере не создаёт. Создайте пять меток состояний и две метки категорий сами, один раз, через `gh label create` или UI трекера, — и ошибка пропадёт. В issue есть ссылка на ветку с общественным исправлением, которую не слили.

**Пяти состояний не хватает. А как же blocked, deferred, implemented?**
Это самый частый пробел, о котором пишут по скиллу. Приходит он в трёх формах:

- Issue полностью описана, но ждёт закрытия другой issue ([#139](https://github.com/mattpocock/skills/issues/139)). Репортёр сказал, что `ready-for-agent` тут «технически верно», но вводит в заблуждение: агент её берёт и застревает.
- Будущая работа, задуманная, но ждущая триггера, поэтому пока не действенная ([#297](https://github.com/mattpocock/skills/issues/297)).
- Терминальное состояние «реализовано, ждёт проверки». Без него AFK-раннер может снова поставить в очередь законченные тикеты.

Случай с блокировкой признан настоящим, но имя не выбрано (`blocked` против `paused`). Ничего из этого не вышло. В обход люди добавляют репозиторную метку рядом с категорией. Слот состояния тогда занимает верное значение, но скилл про добавочную метку не знает. Один общественный форк идёт дальше и добавляет `needs-slicing`, `tracking` и метки трудоёмкости. Работает, но принадлежит форку, а не скиллу.

**Чем это отличается от `diagnosing-bugs`?**
Шаг проверки здесь намеренно мелкий. Он отвечает «это правда и примерно где живёт», а первопричину не ищет. Если баг не воспроизводится по шагам репортёра за несколько минут, ставьте `needs-info` — или берите [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs), если хотите разбираться прямо сейчас. Текст ни одного из скиллов пока не упоминает другой. Об этом пробеле сообщил пользователь, и он всё ещё открыт.

**Можно направить его на весь бэклог и оставить работать?**
Спросить можно, но смотрите, что он читает. Проход «покажи, что требует внимания» — дешёвый листинг для *отбора*. Вы выбираете одну issue, и только потом `triage` собирает по ней полный [контекст](https://www.aihero.dev/ai-coding-dictionary/context). Если прогнать его по двадцати issue сразу, агент может взять этот дешёвый листинг единственным доказательством — и не сказать вам об этом. Листинг возвращает тела issue, но не комментарии. Один пользователь попал ровно в это: у трёх issue уже был комментарий «уже исправлено, предлагаю закрыть», и все три получили новые брифы для агента. Для массового прохода скажите явно, что он обязан читать комментарии к каждой issue.

**Работает с Linear или только с GitHub Issues?**
С любым. Трекер — это конфиг, а не захардкоженное допущение. Его гоняют против Linear (через CLI `linear`), GitLab и простых markdown-файлов в `.scratch/`. Частое разделение: Linear для issue и планирования, GitHub для кода и PR. Скиллы, которые говорят «трекер issue», тогда отображаются на Linear, а те, что говорят «PR», — на GitHub. У локального markdown-трекера есть открытый баг шаблона: в сгенерированном файле критерии приёмки могут оказаться дважды — на верхнем уровне и внутри брифа для агента ([#200](https://github.com/mattpocock/skills/issues/200)).

## Признаки, что работает

- Каждый элемент, которого он коснулся, заканчивается ровно одной ролью категории и ровно одной ролью состояния — не нулём и не двумя конфликтующими состояниями.
- Он даёт рекомендацию с обоснованием и останавливается. Он не переставляет метку и не идёт дальше.
- Он воспроизвёл баг или выкачал и прогнал PR до того, как что-то дошло до `ready-for-agent`.
- Брифы, которые он пишет, называют типы и поведение и не содержат ни путей к файлам, ни номеров строк.
- Когда запрос, отвергнутый полгода назад, возвращается, он говорит об этом и цитирует старую причину, вместо того чтобы разбирать запрос заново.
- Каждый его комментарий начинается с `> *This was generated by AI during triage.*`

## Место в процессе

`triage` — **въездная полоса**, а не шаг основной цепочки. Основной поток начинается с вашей идеи (grill, spec, tickets, implement, review). `triage` — параллельная полоса для работы, пришедшей от кого-то другого. Обе полосы заканчиваются в одном месте: issue с меткой `ready-for-agent` и брифом на ней. [implement](https://aihero.dev/skills-implement) подхватывает это так же, как подхватывает тикет из [to-tickets](https://aihero.dev/skills-to-tickets). Когда запросу не хватает деталей, чтобы `triage` мог написать бриф, `triage` гоняет [гриллинг](https://aihero.dev/skills-grilling) и [domain-modeling](https://aihero.dev/skills-domain-modeling) вместе, по одному раунду вопросов за раз, и записывает решения в `GLOSSARY.md` и ADR по мере того, как вы их принимаете. Когда неясно, в какой вы полосе, маршрут даёт [ask-matt](https://aihero.dev/skills-ask-matt).

## Пример

Человек пишет: «в трекере накопились репорты от чужих людей, покажи, что требует моего внимания». Агент делает дешёвый листинг для отбора — только тела issue, без комментариев. Вы выбираете #42. По ней агент собирает полный контекст, воспроизводит баг по шагам репортёра, прогоняет проверку избыточности по доменному концепту и проверку прежнего отказа по `.out-of-scope/`, затем выдаёт рекомендацию: категория `bug`, состояние `ready-for-agent`, бриф с типами, сигнатурами и контрактом поведения — без путей и номеров строк — и всё это без единой правки в трекере.

Вы соглашаетесь, и он публикует бриф комментарием, начиная его обязательной строкой:

```md
> *This was generated by AI during triage.*
```

и ставит `bug` + `ready-for-agent`. Что получается: issue #42 — с подтверждённым воспроизведением, брифом-контрактом и меткой `ready-for-agent`; AFK-агент может брать её в работу сразу. Соседняя #43, где не хватило деталей, уходит в `needs-info` с конкретным вопросом репортёру.

## Грабли

- **Гоняют `triage` по тикетам из `to-tickets`.** Они уже готовы к агенту: `to-tickets` сам ставит `ready-for-agent` при публикации. Повторный триаж только жжёт контекст и время.
- **Массовый проход по всему бэклогу.** Листинг «что требует внимания» — дешёвый и без комментариев, и агент может принять его за единственное доказательство. Три issue с комментарием «уже исправлено» так и получили новые брифы. Для пакетного прохода требуйте явно читать комментарии к каждой issue.
- **Метки не созданы в трекере.** `setup-matt-pocock-skills` пишет словарь меток в `docs/agents/triage-labels.md`, но сами метки не создаёт: пять меток состояний и две категории заведите один раз через `gh label create` или UI трекера.
- **Ждут, что агент возьмёт скилл сам.** Он вызывается человеком: модель к нему не тянется. В DSH скиллы лежат в `~/.dsh/skills`, а скиллы с `disable-model-invocation` модели вообще не видны — их запускает только человек.
- **Расчёт на автоматику вокруг скилла.** Хуков Claude Code в DSH нет, поэтому ни статус issue после работы агента, ни метки сами не обновятся: закрывайте и переставляйте вручную. И помните про лимит: одновременно активных субагентов (инструмент `subagent`) в DSH не больше 8 — флот «по одному на issue» просто не стартует целиком.
