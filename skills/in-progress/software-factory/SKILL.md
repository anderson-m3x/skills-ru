**Программная фабрика** — это система агентов, которая превращает тикеты, PR и расписания в смерженный код, развёрнутый на удалённой инфраструктуре, которую выбирает пользователь. Этот скилл — язык для её проектирования. Используй эти термины и только их, когда обсуждаешь фабрику или рисуешь её на доске; когда пользователь тянется к слову из раздела _Избегай_, назови канонический термин.

## Задачи и запуски

**Задача** (task):
Вид работы, которую выполняет фабрика: определяется один раз и запускается многократно: review, explore, implement, ratchet. Задача может работать с тикетом, с PR или с кодовой базой в целом.
_Избегай_: «работа», «воркфлоу», «экшен» как названий задачи. Файл воркфлоу у CI-вендора и его job'ы — это место, где задача подключена, а не сама задача.

**Триггер** (trigger):
Событие, которое начинает запуск: изменение в трекере тикетов или в git-хосте, таймер в оркестраторе или другой запуск.

**Запуск** (run):
Одно исполнение задачи на одном раннере — от её триггера до её завершения, — рассматриваемое как чёрный ящик. Запуск порождает следующие запуски либо напрямую, через логику в оркестраторе, либо изменением трекера тикетов или git-хоста. Запуск никогда не ждёт человека: он завершается, а последующее изменение трекера тикетов или git-хоста человеком запускает новый запуск.
_Избегай_: «сессия»

**Раннер** (runner):
Одноразовая машина, на которой исполняется запуск. Ничто на ней не переживает запуск, даже если сама машина долгоживущая: единственная память запуска о более ранних запусках — это трекер тикетов, git-хост и оркестратор.
_Избегай_: «сервер», «хост», «бокс», «вычислитель», «песочница»

## Сервисы

**Трекер тикетов** (ticket tracker):
Место, где живут тикеты, и человеческий интерфейс фабрики: люди планируют работу, создавая тикеты, разговаривают с агентами в их комментариях, а их изменения тикетов запускают запуски.
_Избегай_: «трекер задач», «менеджер тикетов», «проектная доска»

**Источник тикетов** (ticket source):
Всё, что находится вне фабрики и создаёт тикеты в трекере тикетов: кнопка обратной связи, монитор, трекер ошибок, инбокс.
_Избегай_: «источник данных», «источник триггеров», «приём»

**Git-хост** (git host):
Место, где живут ветки, PR и ревью.
_Избегай_: «хост кода», «форж», «репозиторий»

**Оркестратор** (orchestrator):
Компонент, который принимает триггеры, запускает запуски на раннерах и ведёт учёт того, какие запуски в очереди, в работе или завершены.
_Избегай_: «диспетчер», «планировщик», «control plane»

**Платформа наблюдаемости** (observability platform):
Место, куда раннеры отправляют логи, трейсы и статус, чтобы человек мог видеть, что происходило внутри каждого запуска. Необязательна: продукт, занимающий слот раннера или оркестратора, часто показывает достаточно и сам по себе. Запуск никогда не принимает решения на её основе, пока что-то не запишет это в трекер тикетов или в git-хост.
_Избегай_: «наблюдаемость», «логи», «мониторинг», «дашборд»

## Проектирование фабрики

У проекта две половины: **сервисы**, каждый из которых — слот, заполненный продуктом, и **задачи**, чьи запуски двигают работу через эти сервисы.

Отталкивайся от проблемы пользователя, а не от фабрики: неразобранные тикеты, PR, ждущие автоматического ревью, более строгая автоматическая проверка, на которую надо перейти, баги, которые никто не читает. Когда пользователь называет проблему или не знает, что строить, прочитай [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md) — там задачи, решающие типичные из них.

### Начинай медленно

Каждый триггер — это ускоритель. Ускорители без тормозов производят слоп-пушку. Тормозов три:

- **Автоматические проверки**: детерминированные ворота (типы, линт, тесты), которые должен пройти каждый запуск.
- **Автоматическое ревью**: отдельный запуск, который читает диф холодным взглядом на соответствие стандартам кодовой базы и тикету, если он есть.
- **Человеческое ревью**: человек читает PR до мержа; то, что оно ловит, становится новыми автоматическими проверками и более острым автоматическим ревью.

Добавляй по одному автоматическому триггеру за раз, сначала с дросселированием (один баг-репорт из десяти, таймер раз в день) и с человеческим ревью на каждом PR. Открывай дроссель по мере того, как тормоза заслуживают доверия, и ограничивай каждый цикл запусков несколькими попытками, прежде чем вмешается человек.

### Заполняй каждый слот

Каждый сервис — это слот. Один продукт может заполнять несколько слотов, а один сервер может хостить несколько сервисов. Три проекта рядом:

| Сервис                 | Всё на GitHub                          | Тикеты в Linear                | Свой трекер              |
| ---------------------- | -------------------------------------- | ------------------------------ | ------------------------ |
| Трекер тикетов         | GitHub Issues                          | Linear                         | собственное приложение   |
| Источник тикетов       | кнопка обратной связи                  | кнопка обратной связи, монитор | кнопка обратной связи, монитор |
| Git-хост               | GitHub                                 | GitHub                         | GitHub                   |
| Оркестратор            | GitHub Actions                         | собственный сервер + база данных | собственное приложение |
| Раннер                 | раннер Actions                         | Actions, E2B, Daytona или VPS  | собственное приложение или песочницы |
| Платформа наблюдаемости | нет: страниц запусков Actions достаточно | платформа трейсинга LLM        | собственное приложение   |

Когда пользователь выбирает продукт для слота, прочитай обзор этого слота, чтобы сориентироваться, а затем исследуй актуальные варианты сам; каждый обзор группирует варианты по типам и перечисляет вопросы, которые решают судьбу слота:

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

Покупай сервисы и строй задачи: задачи несут проект пользователя, сервисы универсальны. Предпочитай готовый трекер тикетов: он надёжен, люди его уже знают, и внешних пользователей легко пустить.

### Допрашивай каждую задачу

Для каждой задачи ответь:

1. Что её запускает?
2. Что она делает и какие сервисы читает и пишет?
3. Что она запускает дальше?
4. Где возвращается человек?
5. Что мешает двум запускам делать одну и ту же работу?

Для каждого источника тикетов ответь: что мешает ему завести один и тот же тикет дважды?

Проект готов, когда каждый слот называет продукт (или, для платформы наблюдаемости, осознанное «ничего») и у каждой задачи и каждого источника тикетов есть ответ на каждый вопрос.
