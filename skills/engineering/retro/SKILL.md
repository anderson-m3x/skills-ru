Пользователь попросил **ретроспективу**. Ты предлагаешь улучшения **окружения** агента-кодера, чтобы улучшить будущие прогоны.

## Шаги

1. Вызови инструмент skill с `writing-for-agents`, чтобы получить руководство по стилю письма.

2. Прочитай первоисточники по сессии, которую указал пользователь. Это может означать поиск по логам сессий на этой машине. Если пользователь не указал сессию, по умолчанию бери текущую.

3. Ищи кандидатов на улучшение в этих категориях.

- **Навигация**: насколько легко агенту было находить нужные файлы? Есть ли скрытые зависимости между файлами? Упростил ли бы задачу **навигационный указатель**? _Используй, когда_ сессия долго искала кусочек информации.
- **Автоматические проверки**: есть ли автоматические проверки, которые поймали бы ошибки агента? Линтинг, типизация, тесты, линтеры файловой системы? Сначала прочитай собственную команду проверки репозитория (его скрипты `lint`/`check` в `package.json`/build-инструменте, его CI-workflow), чтобы находкой была «проверка уже существует, но не подключена или молча сломана», а не её переизобретение. Репозиторий без **ограждения** (без pre-commit хука и без CI-джобы, запускающей его команду lint/typecheck/test) — сам по себе является находкой: нелинтированный репозиторий — это постоянная упущенная возможность, а не нейтральный дефолт. _Используй, когда_ агент сделал ошибку, которую поймала бы автоматическая проверка, или в репозитории вообще нет ограждения.
- **Стандарты кодинга**: нужно ли дать **агенту-ревьюеру** новое правило для соблюдения? Нужно ли удалить или уточнить существующее правило? Сначала классифицируй нарушение: **механическое** (фиксированный синтаксический паттерн, запрещённый API, форма импорта, правило расположения файлов) получает детерминированную проверку, и точка: кастомное правило в линтере самого репозитория, новый pre-commit хук или новая CI-джоба — что дешевле в языке и существующем ограждении этого репозитория. По умолчанию строй проверку, а не пиши правило. Оставляй `CODING_STANDARDS.md` для настоящих **суждений** (сквозная согласованность между файлами, «соответствует окружающему стилю», всё, что никакое ограждение не заменит). _Используй, когда_ агент-ревьюер не поймал ошибку.
- **Глобальный AGENTS.md**: есть ли направляющие инструкции, которые стоит перенести в стандарты кодинга (или в автоматические проверки) вместо этого? _Используй, когда_ файл AGENTS.md особенно велик — в репозитории ИЛИ в глобальной области пользователя.
- **Экономия инструментов**: делал ли агент дорогие вызовы инструментов, которые можно было бы рационализировать? Есть ли кастомный инструментарий (CLI, MCP), особенно неэффективный по токенам? _Используй, когда_ агент сделал дорогой вызов инструмента.
- **Пустые операции**: ищи в направляющих файлах инструкции, которые не меняют поведение агента. _Используй, когда_ направляющие файлы большие и неудобные.
- **Доступ к информации**: ищи возможности расширить доступ агента к информации. Дублирование логов дев-сервера в файл, доступ только на чтение к сторонним сервисам. _Используй, когда_ агенту не хватало важного кусочка информации.

4. Представь этих кандидатов пользователю, по порядку серьёзности.

## Справочно

### Реализация против ревью

Помни, что вся работа проходит две стадии: реализацию и ревью. У агента-реализатора самое сильное **давление контекста**. Он отвечает за исследование, написание кода и отладку падений.

У агента-ревьюера давление контекста наименьшее — он получает diff, так что исследовать не нужно. Ему часто не нужно писать код или отлаживать.

Это значит, что агент-ревьюер должен отвечать за навязывание стандартов кодинга, а не агент-реализатор.

### Файлы

В репозитории тебе доступны несколько файлов:

- `AGENTS.md`: этот файл попадает в контекстное окно любого агента, работающего в этом репозитории. Его следует использовать крайне скупо, обычно только для **навигационных указателей** на другие файлы.
- `CODING_STANDARDS.md`: этот файл читается во время ревью, а не реализации. Добавляй **навигационные указатели** на папки с документацией, если файл стандартов вырастает больше 1 000 строк.
- Документация: используй её как файлы-справочники, на которые указывают другие файлы. Прежде чем писать новую документацию, поищи существующую.
- Скиллы: используй скиллы для документации (поскольку их description попадает в контекстное окно агента) или для команд, вызываемых пользователем. Следуй советам скилла `writing-for-agents`.
