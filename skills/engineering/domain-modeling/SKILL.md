# Доменное моделирование

Активно строй и заостряй доменную модель проекта по ходу проектирования. Это *активная* дисциплина: оспаривать термины, придумывать сценарии с краевыми случаями и записывать глоссарий и решения в тот момент, когда они кристаллизуются. (Просто *чтение* `GLOSSARY.md` ради словаря — не этот скилл: это привычка в одну строку, доступная любому скиллу. Этот скилл — для случаев, когда ты меняешь модель, а не просто потребляешь её.)

## Структура файлов

У большинства репозиториев один контекст:

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

Если в корне есть `GLOSSARY-MAP.md`, у репозитория несколько контекстов. Карта указывает, где живёт каждый из них:

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← системные решения
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← решения конкретного контекста
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

Создавай файлы лениво: только когда есть что записать. Если `GLOSSARY.md` нет, создай его, когда разрешён первый термин. Если `docs/adr/` нет, создай его, когда нужен первый ADR.

## По ходу сессии

### Оспаривай по глоссарию

Когда пользователь использует термин, конфликтующий с существующим языком в `GLOSSARY.md`, сразу укажи на это. «Твой глоссарий определяет 'cancellation' как X, а ты, похоже, имеешь в виду Y. Что из этого?»

### Заостряй размытый язык

Когда пользователь использует расплывчатые или перегруженные термины, предложи точный каноничный термин. «Ты говоришь 'account': ты имеешь в виду Customer или User? Это разные вещи.»

### Обсуждай конкретные сценарии

Когда обсуждаются доменные связи, нагружай их конкретными сценариями. Придумывай сценарии, которые прощупывают краевые случаи и заставляют пользователя быть точным в границах между понятиями.

### Сверяйся с кодом

Когда пользователь утверждает, как что-то работает, проверь, согласен ли код. Если находишь противоречие, вынеси его наверх: «Твой код отменяет заказы целиком, но ты только что сказал, что возможна частичная отмена. Что верно?»

### Обновляй GLOSSARY.md сразу

Когда термин разрешён, обнови `GLOSSARY.md` тут же. Не накапливай это пачками: фиксируй по мере появления. Используй формат из [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md).

`GLOSSARY.md` должен быть полностью лишён деталей реализации. Не относись к `GLOSSARY.md` как к спеке, черновику или хранилищу решений по реализации. Это глоссарий и ничего больше.

### Предлагай ADR скупо

Предлагай создать ADR, только когда верны все три условия:

1. **Трудно откатить**: цена смены решения позже значима
2. **Удивительно без контекста**: будущий читатель будет спрашивать «почему они сделали именно так?»
3. **Результат настоящего компромисса**: были реальные альтернативы, и ты выбрал одну по конкретным причинам

Если чего-то из трёх не хватает, пропусти ADR. Используй формат из [ADR-FORMAT.md](./ADR-FORMAT.md).
