# Настройка скиллов Мэтта Покока

Создай для репозитория каркас конфигурации, на которую рассчитывают инженерные скиллы:

- **Трекер задач**: где живут задачи (по умолчанию GitHub; локальный markdown тоже поддерживается из коробки)
- **Метки триажа**: строки, используемые для пяти канонических ролей триажа
- **Доменная документация**: где живут `GLOSSARY.md` и ADR, а также правила их чтения для потребителей

Это скилл, управляемый промптом, а не детерминированный скрипт. Исследуй, покажи найденное, подтверди у пользователя, а затем пиши.

## Процесс

### 1. Исследование

Посмотри на текущий репозиторий, чтобы понять его исходное состояние. Читай то, что есть; ничего не предполагай:

- `git remote -v` и `.git/config`: это GitHub-репозиторий? Какой именно?
- `AGENTS.md` в корне репозитория: существует ли он? Есть ли в нём уже раздел `## Agent skills`?
- `GLOSSARY.md` и `GLOSSARY-MAP.md` в корне репозитория, а также устаревшие `CONTEXT.md` / `CONTEXT-MAP.md`. Если устаревший файл существует, предложи переименовать его через `git mv` в имя с `GLOSSARY` и переписать эти имена в `docs/agents/domain.md`.
- `docs/adr/` и любые каталоги `src/*/docs/adr/`
- `docs/agents/`: существует ли уже вывод предыдущего запуска этого скилла?
- `.scratch/`: признак того, что соглашение о локальном markdown-трекере задач уже используется
- Установлен ли скилл `triage`? (папка скилла `triage` рядом с этой или `triage` среди доступных тебе скиллов.) От этого зависит, будет ли вообще выполняться раздел B.
- Признаки монорепозитория: `pnpm-workspace.yaml`, поле `workspaces` в `package.json` или заполненный `packages/*` со своим `src/`. Они встречаются только в действительно большом многопакетном репозитории; их отсутствие означает единственный контекст, а это почти любой репозиторий.

### 2. Покажи находки и спроси

Кратко перечисли, что есть и чего не хватает. Затем проходи разделы по порядку. Один раздел — один ответ, потом следующий.

Начинай каждый раздел с рекомендованного ответа, чтобы пользователь мог согласиться одним словом. Однострочное пояснение давай только тогда, когда выбор действительно разветвляется; пропускай раздел целиком, если исследование уже всё решило (раздел B, когда `triage` не установлен, раздел C, когда монорепозитория нет).

**Раздел A: Трекер задач.**

> Пояснение: «трекер задач» — это то место, где живут задачи этого репозитория. Скиллы вроде `to-tickets`, `triage` и `to-spec` читают из него и пишут в него. Им нужно знать, вызывать ли `gh issue create`, писать markdown-файл в `.scratch/` или следовать какому-то другому описанному тобой рабочему процессу. Выбери место, где ты на самом деле отслеживаешь работу по этому репозиторию.

Исходная установка: эти скиллы спроектированы под GitHub. Если `git remote` указывает на GitHub, предложи его. Если `git remote` указывает на GitLab (`gitlab.com` или самостоятельно размещённый хост), предложи GitLab. В остальных случаях (или если пользователь предпочитает) предложи:

- **GitHub**: задачи живут в GitHub Issues репозитория (используется CLI `gh`)
- **GitLab**: задачи живут в GitLab Issues репозитория (используется CLI [`glab`](https://gitlab.com/gitlab-org/cli))
- **Локальный markdown**: задачи живут как файлы в `.scratch/<feature>/` этого репозитория (подходит для сольных проектов или репозиториев без remote)
- **Другое** (Jira, Linear и т. п.): попроси пользователя описать рабочий процесс одним абзацем; скилл запишет его как свободный текст

Запиши выбор в `docs/agents/issue-tracker.md`. Шаблоны GitHub и GitLab содержат флаг «PR как поверхность запросов», по умолчанию **выключенный**. Оставь его выключенным и не поднимай этот вопрос: пользователь, который хочет видеть внешние PR в очереди триажа, может переключить флаг в файле позже.

Трекеру GitHub или GitLab нужен достижимый репозиторий. Если пользователь выбрал один из них, а ни один `git remote` не указывает на этот хост, возьми у него URL репозитория и подключи его (`git init`, если нужно, `git remote add origin <url>`) прежде чем идти дальше. Готово, когда `gh repo view` / `glab repo view` печатает проект изнутри этого каталога; если не печатает, остановись и скажи пользователю, чего не хватает.

**Раздел B: Словарь меток триажа.** Пропусти этот раздел целиком, если скилл `triage` не установлен (об этом тебе сказало исследование), поскольку неустановленному скиллу метки не нужны.

Если он установлен, задай ровно один вопрос:

> Хочешь оставить метки триажа по умолчанию? (рекомендуется: **да**)

По умолчанию используются пять канонических ролей, каждая строка метки равна своему имени: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. При ответе **да** запиши их как есть. Только если пользователь сказал нет, обычно потому что в его трекере уже используются другие имена (например, `bug:triage` для `needs-triage`), собери переопределения, чтобы `triage` применял существующие метки, а не создавал дубликаты.

**Раздел C: Доменная документация.** По умолчанию — **единственный контекст** (один `GLOSSARY.md` + `docs/adr/` в корне репозитория). Это подходит почти любому репозиторию; пиши так, не спрашивая.

Предлагай **несколько контекстов** (корневой `GLOSSARY-MAP.md`, указывающий на `GLOSSARY.md` каждого контекста) только если исследование нашло признаки монорепозитория. Тогда уточни, какую структуру они хотят.

### 3. Подтверди и отредактируй

Покажи пользователю черновик:

- Блок `## Agent skills`, который нужно добавить в редактируемый файл инструкций для агентов (о правилах выбора см. шаг 4)
- Содержимое `docs/agents/issue-tracker.md`, `docs/agents/domain.md` и `docs/agents/triage-labels.md` (последний — только когда установлен `triage`)

Дай им возможность отредактировать до записи.

### 4. Запись

**Выбери файл для редактирования:**

- Если `AGENTS.md` существует, редактируй его.
- Если его нет, спроси пользователя, создавать ли `AGENTS.md`; не выбирай за него.

Если файл инструкций для агентов уже существует, всегда редактируй его и никогда не создавай второй такой файл.

Если блок `## Agent skills` уже существует в выбранном файле, обнови его содержимое на месте, а не дописывай дубликат. Не перезаписывай пользовательские правки в окружающих разделах.

Блок:

```markdown
## Agent skills

### Issue tracker

[one-line summary of where issues are tracked]. See `docs/agents/issue-tracker.md`.

### Triage labels

[one-line summary of the label vocabulary]. See `docs/agents/triage-labels.md`.

### Domain docs

[one-line summary of layout: "single-context" or "multi-context"]. See `docs/agents/domain.md`.
```

Включай подблок `### Triage labels` и пиши `docs/agents/triage-labels.md` только когда `triage` установлен и раздел B выполнялся. Когда нет — оба пропускаются.

Когда раздел B выполнялся на GitHub или GitLab, создай каждую настроенную метку, которой не хватает в трекере (`gh label create` / `glab label create`).

Затем напиши файлы документации, взяв за отправную точку шаблоны-заготовки в папке этого скилла:

- [issue-tracker-github.md](./issue-tracker-github.md): трекер задач GitHub
- [issue-tracker-gitlab.md](./issue-tracker-gitlab.md): трекер задач GitLab
- [issue-tracker-local.md](./issue-tracker-local.md): локальный markdown-трекер задач
- [triage-labels.md](./triage-labels.md): сопоставление меток (только если установлен `triage`)
- [domain.md](./domain.md): правила чтения доменной документации для потребителей + структура

Для «других» трекеров задач напиши `docs/agents/issue-tracker.md` с нуля, исходя из описания пользователя.

### 5. Готово

Скажи пользователю, что настройка завершена, и какие инженерные скиллы теперь будут читать эти файлы. Упомяни, что он может позже редактировать `docs/agents/*.md` напрямую; повторно запускать этот скилл нужно, только если он хочет сменить трекер задач или начать с нуля.
