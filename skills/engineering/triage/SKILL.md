# Триаж

Проводите issue в трекере задач проекта через небольшой конечный автомат ролей триажа.

Если в этом репозитории внешние PR считаются поверхностью для запросов (см. конфиг трекера задач), триаж покрывает и их: **PR — это issue с приложенным кодом**, те же роли, те же состояния и тот же автомат, плюс несколько отличий, помеченных ниже как «для PR». Голый `#42` резолвится в issue или PR согласно конфигу трекера.

Каждый комментарий или issue, опубликованный в трекере задач в ходе триажа, **обязан** начинаться с этой оговорки:

```
> *Сгенерировано ИИ в ходе триажа.*
```

## Справочные документы

- [AGENT-BRIEF.md](AGENT-BRIEF.md): как писать долговечные брифы для агента
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): как работает база знаний `.out-of-scope/`

## Роли

Две роли **категории**:

- `bug`: что-то сломано
- `enhancement`: новая функциональность или улучшение

Пять ролей **состояния**:

- `needs-triage`: мейнтейнеру нужно оценить
- `needs-info`: ждём от репортёра дополнительной информации
- `ready-for-agent`: полностью специфицировано, готово для AFK-агента
- `ready-for-human`: требует реализации человеком
- `wontfix`: не будет реализовано

Для PR те же состояния читаются относительно приложенного кода: `ready-for-agent` значит, что приложен бриф и агент должен сделать следующий шаг по диффу; `ready-for-human` значит, что PR готов к мержу человеком.

Каждый прошедший триаж issue должен нести ровно одну роль категории и одну роль состояния. Если роли состояния противоречат друг другу, отметьте это и спросите мейнтейнера, прежде чем что-либо делать.

Это канонические имена ролей. Реальные строки меток в трекере задач могут отличаться. Соответствие должно было быть вам передано. Если нет — скажите пользователю запустить скилл setup-matt-pocock-skills.

Переходы состояний: issue без меток обычно сначала попадает в `needs-triage`; оттуда оно уходит в `needs-info`, `ready-for-agent`, `ready-for-human` или `wontfix`. Из `needs-info` оно возвращается в `needs-triage`, как только репортёр ответит. Мейнтейнер может переопределить переход в любой момент; отмечайте переходы, которые выглядят необычно, и спрашивайте перед тем, как продолжить.

## Вызов

Мейнтейнер вызывает скилл triage и описывает, чего хочет, обычным языком. Интерпретируйте запрос и действуйте. Примеры:

- «Покажи всё, что требует моего внимания»
- «Давай посмотрим на #42» (issue или PR)
- «Переведи #42 в ready-for-agent»
- «Что готово к тому, чтобы агенты взяли?»

## Показать, что требует внимания

Запросите трекер задач и покажите три корзины, сначала самые старые:

1. **Без меток**: триаж никогда не проводился.
2. **`needs-triage`**: идёт оценка.
3. **`needs-info` с активностью репортёра после последних заметок триажа**: нужна повторная оценка.

Когда PR в скоупе, включайте внешние PR в эти корзины и помечайте каждую строку `[PR]` или `[issue]`. Обнаружение показывает только *внешние* PR (конфиг трекера определяет, кто считается внешним), поэтому PR соавтора, находящийся в работе, — не работа по триажу. Этот фильтр относится только к обнаружению; явно названный PR всегда проходит триаж независимо от автора.

Покажите счётчики и однострочную сводку по каждому пункту. Пусть мейнтейнер выберет.

## Триаж конкретного issue или PR

1. **Соберите контекст.** Прочитайте issue или PR целиком (тело, комментарии, метки, автор, даты; для PR — ещё и дифф). Разберите предыдущие заметки триажа, чтобы не переспрашивать уже решённое. Исследуйте кодовую базу, опираясь на доменный глоссарий проекта и соблюдая ADR в соответствующей области. Выполните две проверки по кодовой базе: (a) **избыточность**: ищите существующую реализацию запрошенного поведения по доменному понятию (а не только по формулировке запроса) и сообщите, где искали. Если нашли — это уже реализованный `wontfix` (шаг 5). (b) **предыдущий отказ**: прочитайте `.out-of-scope/*.md` и покажите всё, что похоже на этот запрос.

2. **Порекомендуйте.** Сообщите мейнтейнеру свою рекомендацию по категории и состоянию с обоснованием, плюс краткую сводку по кодовой базе, релевантную запросу (включая то, реализовано ли это уже). Дождитесь указаний.

3. **Проверьте утверждение.** Прежде чем гриллить, убедитесь, что утверждение выдерживает проверку. Для бага воспроизведите его по шагам репортёра. Для PR подтвердите, что дифф делает то, что заявлено: выкачайте его, прогоните релевантные тесты или команды. Сообщите, что получилось: подтверждено (с путём в коде), не удалось, или недостаточно деталей (сильный сигнал `needs-info`). Подтверждённая проверка делает бриф для агента заметно сильнее.

4. **Грилл (если нужно).** Если запрос нужно додумать, вызовите инструмент skill дважды — для скиллов «grilling» и «domain-modeling» — и отшлифуйте его вопросами, раунд за раундом, уточняя доменные термины и по ходу обновляя `GLOSSARY.md`/ADR по мере принятия решений.

5. **Примените результат:**
   - `ready-for-agent`: опубликуйте комментарий с брифом для агента ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: та же структура, что у брифа для агента, но с пометкой, почему это нельзя делегировать (суждения, внешний доступ, проектные решения, ручное тестирование).
   - `needs-info`: опубликуйте заметки триажа (шаблон ниже).
   - Для `wontfix` закройте issue; комментарий зависит от того, *почему*:
     - **Уже реализовано**: изменение уже есть в кодовой базе. Укажите, где оно находится; **не** пишите в `.out-of-scope/` (эта база — для *отклонённых* запросов, а не для реализованных).
     - **Отклонено (баг)**: вежливо объясните, затем закройте.
     - **Отклонено (enhancement)**: запишите в `.out-of-scope/`, дайте ссылку из комментария, затем закройте ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: примените роль. Комментарий необязателен, если есть частичный прогресс.

## Быстрое переопределение состояния

Если мейнтейнер говорит «переведи #42 в ready-for-agent», доверьтесь ему и примените роль сразу. Подтвердите, что собираетесь сделать (смена роли, комментарий, закрытие), затем действуйте. Грилл-сессию пропустите. Если переводите в `ready-for-agent` без грилл-сессии, спросите, не хотят ли они написать бриф для агента.

## Шаблон для needs-info

```markdown
## Заметки триажа

**Что мы уже выяснили:**

- пункт 1
- пункт 2

**Что нам ещё нужно от вас (@reporter):**

- вопрос 1
- вопрос 2
```

Всё, что выяснено в ходе грилл-сессии, заносите в раздел «что уже выяснили», чтобы работа не пропала. Вопросы должны быть конкретными и выполнимыми, а не «дайте больше информации».

## Возобновление предыдущей сессии

Если на issue или PR уже есть заметки триажа, прочитайте их, проверьте, ответил ли репортёр на оставшиеся вопросы, и покажите обновлённую картину, прежде чем продолжать. Не переспрашивайте про уже решённое.
