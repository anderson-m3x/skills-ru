# Проектирование кодовой базы

Проектируй **глубокие модули**: много поведения за маленьким интерфейсом, размещённым на чистом шве, тестируемым через этот интерфейс. Используй этот язык и эти принципы везде, где код проектируется или перестраивается. Цель — рычаг для вызывающих, локальность для сопровождающих и тестируемость для всех.

## Глоссарий

Используй эти термины точно: не подменяй их словами «компонент», «сервис», «API» или «граница». Согласованность языка — в этом весь смысл.

**Модуль**: всё, что имеет интерфейс и реализацию. Осознанно не привязан к масштабу: функция, класс, пакет или срез, пересекающий уровни. _Избегай_: unit, компонент, сервис.

**Интерфейс**: всё, что вызывающий должен знать, чтобы правильно использовать модуль: сигнатура типа, но также инварианты, ограничения порядка, режимы ошибок, требуемая конфигурация и характеристики производительности. _Избегай_: API, сигнатура (слишком узко, они относятся лишь к поверхности уровня типов).

**Реализация**: то, что внутри модуля, его тело кода. Отличается от **адаптера**: вещь может быть маленьким адаптером с большой реализацией (репозиторий на Postgres) или большим адаптером с маленькой реализацией (фейк в памяти). Тянись к «адаптеру», когда тема — шов; иначе — к «реализации».

**Глубина**: рычаг на интерфейсе. Объём поведения, который вызывающий (или тест) может задействовать на единицу интерфейса, который ему приходится изучать. Модуль **глубокий**, когда за маленьким интерфейсом стоит много поведения, и **мелкий**, когда интерфейс почти так же сложен, как реализация.

**Шов** _(Michael Feathers)_: место, где можно изменить поведение, не редактируя в этом месте; *локация*, в которой живёт интерфейс модуля. Куда положить шов — отдельное проектное решение, отличное от того, что стоит за ним. _Избегай_: граница (перегружено ограниченным контекстом из DDD).

**Адаптер**: конкретная вещь, удовлетворяющая интерфейсу на шве. Описывает *роль* (какой слот заполняет), а не субстанцию (что внутри).

**Рычаг**: то, что вызывающие получают от глубины. Больше возможностей на единицу изученного интерфейса. Одна реализация окупается на N местах вызова и M тестах.

**Локальность**: то, что сопровождающие получают от глубины. Изменения, баги, знания и проверка концентрируются в одном месте, а не расползаются по вызывающим. Исправил один раз — исправлено везде.

## Глубокий против мелкого

**Глубокий модуль** = маленький интерфейс + много реализации:

```
┌─────────────────────┐
│    Малый интерфейс  │  ← Мало методов, простые параметры
├─────────────────────┤
│                     │
│ Глубокая реализация │  ← Сложная логика скрыта
│                     │
└─────────────────────┘
```

**Мелкий модуль** = большой интерфейс + мало реализации (избегай):

```
┌─────────────────────────────────┐
│        Большой интерфейс        │  ← Много методов, сложные параметры
├─────────────────────────────────┤
│  Тонкая реализация              │  ← Только пробрасывает дальше
└─────────────────────────────────┘
```

Проектируя интерфейс, спроси:

- Можно ли уменьшить число методов?
- Можно ли упростить параметры?
- Можно ли спрятать больше сложности внутрь?

## Принципы

- **Глубина — свойство интерфейса, а не реализации.** Глубокий модуль может внутри состоять из маленьких, мокируемых, заменяемых частей; просто они не входят в интерфейс. У модуля могут быть **внутренние швы** (приватные для его реализации, используемые его собственными тестами) и **внешний шов** на его интерфейсе.
- **Тест удалением.** Представь, что модуль удалён. Если сложность исчезает — это был проброс. Если сложность снова появляется у N вызывающих — модуль оправдывал своё существование.
- **Интерфейс — это поверхность тестирования.** Вызывающие и тесты пересекают один и тот же шов. Если хочется тестировать *в обход* интерфейса, скорее всего модуль имеет неправильную форму.
- **Один адаптер — гипотетический шов. Два адаптера — настоящий.** Не вводи шов, пока через него действительно ничего не варьируется.

## Проектирование ради тестируемости

Хорошие интерфейсы делают тестирование естественным:

1. **Принимай зависимости, не создавай их.**

   ```typescript
   // Тестируемо
   function processOrder(order, paymentGateway) {}

   // Трудно тестировать
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **Возвращай результаты, не производи побочных эффектов.**

   ```typescript
   // Тестируемо
   function calculateDiscount(cart): Discount {}

   // Трудно тестировать
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **Небольшая площадь поверхности.** Меньше методов — меньше нужно тестов. Меньше параметров — проще подготовка теста.

## Связи

- У **модуля** ровно один **интерфейс** (поверхность, которую он предоставляет вызывающим и тестам).
- **Глубина** — свойство **модуля**, измеряемое относительно его **интерфейса**.
- **Шов** — место, где живёт **интерфейс** **модуля**.
- **Адаптер** находится на **шве** и удовлетворяет **интерфейсу**.
- **Глубина** даёт **рычаг** вызывающим и **локальность** сопровождающим.

## Отвергнутые трактовки

- **Глубина как отношение строк реализации к строкам интерфейса** (Ousterhout): поощряет раздувание реализации. Вместо этого мы используем глубину-как-рычаг.
- **«Интерфейс» как ключевое слово `interface` в TypeScript или публичные методы класса**: слишком узко — здесь интерфейс включает каждый факт, который должен знать вызывающий.
- **«Граница»**: перегружено ограниченным контекстом из DDD. Говори **шов** или **интерфейс**.
